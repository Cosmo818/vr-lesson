# Архитектура платформы (целевая) — проект

Статус: черновик на утверждение. Подчиняется `docs/LAWS.md`. Описывает, как устроены модули, чтобы правка одного не ломала остальные.

## 1. Слои и направление зависимостей

```
Слой 4  Интерфейс:   кабинеты, меню, справка, темы
Слой 3  Модули:      комнаты, редактор, каталог/рейтинг, тесты, модерация, учёт использования
Слой 2  Ядро:        права и роли, события, флаги, ошибки и журнал, схемы данных, миграции
Слой 1  Данные:      хранилище (локально), синхронизация, сервер и база
```

Правило: вызывать можно только слой ниже. Слой выше о нижнем знает только контракт. Снизу вверх связь идёт через события («результат сохранён», «тема сменилась»), а не через прямые вызовы.

## 2. Карта модулей

| Модуль | Отвечает за | Публичный контракт | Зависит от |
|---|---|---|---|
| `schema` | Схемы данных, версии, проверка входа, миграции | `validate(kind, data)`, `migrate(kind, data)` | — |

| `sync` | Обмен с центром и школьным узлом, список серверов | `sync.now()`, события `synced`, `offline` | `store`, `auth` |
| `auth` | Аккаунты, роли, сессии | `auth.can(action, resource)`, `auth.user()` | `schema` |
| `flags` | Переключатели функций | `flags.on(name)` | `store` |
| `errors` | Границы ошибок, журнал | `guard(moduleName, fn, fallbackView)`, `log(err)` | — |
| `theme` | Темы оформления | `theme.apply(id)`, `theme.list()` | `schema`, `store` |
| `engine` | Рендер, ввод, WebXR | `VR.createEngine` (как сейчас) | — |
| `rooms` | Загрузка комнат (встроенные и по RoomSpec) | `VR.ROOMS.*`, `rooms.load(id, version)` | `engine`, `schema`, `store` |

| `catalog` | Каталог, поиск, форки, версии | `catalog.search()`, `catalog.fork()` | `sync`, `auth` |
| `rating` | Оценки и рейтинг | `rating.of(roomId)` | `catalog`, `store` |

`js/chem.js` (Б65, 23.10.2026) — часть слоя `rooms`: ядерная модель `VR.nuc` (чистые функции) и стенд `VR.chemLab`; `ROOMS.chem` вызывает его под флагом `chemLab` и в `try`.

Текущие файлы переезжают в эту карту постепенно: `js/store.js` остаётся `store`, `js/engine.js` — `engine`, `js/rooms*.js` — встроенные комнаты модуля `rooms`. Новые модули добавляются рядом, не меняя старые.

## 3. Как защитить систему от «эффекта домино»

1. **Контрактные проверки.** Для каждого модуля в `tests/` есть проверка его публичного контракта. Правка модуля, которая ломает контракт, видна сразу, до пуша.
2. **Границы ошибок.** Каждый кабинет и каждая вкладка оборачиваются в `guard`. Падение вкладки не трогает остальные.
3. **Валидация на входе.** `schema.validate` вызывается при каждом чтении данных извне. Повреждённая запись отбрасывается и пишется в журнал; система продолжает работать.
4. **Версии схем и миграции.** Любое изменение формата данных — через новую версию схемы и миграцию. Перед миграцией на сервере делается копия базы.
5. **Флаги.** Новая функция выключена, пока не прошла проверку на реальных данных. При проблеме выключаем флаг, а не откатываем релиз.
6. **События вместо прямых вызовов** между слоями (тема сменилась, пользователь вошёл, данные синхронизированы).
7. **Запасной режим.** Встроенная тема, встроенные комнаты и встроенные настройки всегда доступны, если загруженные повреждены.
8. **Автоматическая проверка законов.** Скрипт `tests/laws.js` (предлагается добавить): все файлы из `sw.js` существуют; в публичных файлах нет ключей и адресов; на каждую роль есть проверка прав на сервере; ни один модуль не обращается к слою выше. Падение скрипта запрещает пуш.

## 4. Роли и кабинеты

Иерархия сущностей (школа → директор и экспертный совет → учителя → классы → ученики), матрица прав и инварианты — в `docs/ROLES.md`.

| Кабинет | Для кого | Основное |
|---|---|---|
| Личный кабинет ученика | Ученик | Мой прогресс, награды, мои классы, выбор темы |
| Кабинет учителя | Учитель | Классы и ученики, тесты, свои комнаты и черновики, отчёты, приглашения для отладки |
| Кабинет эксперта | Учитель-эксперт | Очередь проверки комнат, замечания, решение «одобрить / вернуть» |
| Кабинет школьного администратора | Администратор школы | Учителя школы, школьный узел, список шлемов (позже) |
| Кабинет суперадминистратора | Владелец | Пользователи и роли, режим выпуска, темы, флаги, журналы ошибок, резервные копии, учёт использования, выплаты (позже) |

Принципы кабинетов:
- Каждый кабинет — отдельный модуль страницы. Общие кирпичи только через `ui-kit`.
- Кабинет показывает только то, что разрешено роли, но права проверяются на сервере (А10).
- Кабинет суперадминистратора не имеет «кнопок без подтверждения»: сброс, смена роли, публикация идут через окно подтверждения и журнал.
- Режим выпуска комнат (настройка суперадминистратора): «слово владельца после решения экспертов» (по умолчанию) или «автоматически после согласия экспертов».

## 5. Темы оформления

- **Тема — это набор токенов** (цвета, шрифты, радиусы, отступы) и для VR цвета панелей и пресет окружения. Своих стилей и скриптов в теме нет, поэтому тема не может сломать логику.
- **Токены, а не жёсткие цвета.** Весь интерфейс берёт цвета из переменных (`--c-bg`, `--c-text`, …). Прямые цвета в коде не используются.
- **Проверка контраста.** Тема, у которой текст плохо читается на фоне, отклоняется при сохранении, с понятным объяснением (защита от дурака).
- **Встроенные темы:** светлая, тёмная, высококонтрастная, для VR-панелей (читаемая на расстоянии). Запасная тема всегда доступна.
- **Выбор:** тема школы по умолчанию, класса и ученика поверх. Если выбранная тема недоступна, применяется запасная.
- **Свои темы** (позже): школа или учитель создаёт тему из токенов, эксперт не нужен, но проверка контраста обязательна.

## 6. Порядок внедрения (укрупнённо)

1. `schema` + `errors` + `flags` как основание (малые модули, без смены поведения).
2. `tests/laws.js` и контрактные проверки существующих модулей (`store`, `engine`, `rooms`).
3. `theme` и `ui-kit`, перевод существующих страниц на токены.
4. Роли и аккаунты (`auth`), кабинеты по одному.
5. RoomSpec, редактор, каталог, рейтинг, модерация (см. `docs/ROOM_SPEC.md`).
6. Школьный узел, `sync` со списком серверов, учёт использования.

Каждый шаг — отдельная задача, отдельный чат, обновление `HANDOFF.md` в конце. Шаги 1–2 дают устойчивость раньше, чем начнётся новая функциональность.
