# PLAN — VR-урок

## Учётки по ROLES.md

Дата: 22.10.2026. Автор: architect (Opus). Основа: `docs/ROLES.md` разделы 3, 4, 6, 7; `docs/LAWS.md` (А1–А17, Б34, Б41, раздел В); `HANDOFF.md`; `CHECKLIST.md`. Код этим планом не меняется.

Цель: иерархия суперадмин → директор → учитель → ученик, цепочка администрирования, фильтр «регион → школа → класс/учитель» с постраничной таблицей, логин и пароль у взрослых без пароля по умолчанию, журнал аудита, приглашения, совместимость со старыми ключами teacher/device. Работающая школа (`school-default`, ключи teacher/device, пароль страницы учителя) ведёт себя как сейчас, пока владелец не включит учётки.

---

### 1. Решения по архитектуре

**1.1. Учётки живут только на сервере (А11, А10).** Пользователи, роли, сессии, приглашения, школы и журнал — серверные таблицы, они НЕ входят в синхронизируемое состояние и НЕ проходят через `merge`/`merge_in`. Причина: хэши паролей не должны попадать в `localStorage` шлема и на другие устройства; один источник правды — сервер. Компромисс: кабинет директора работает только онлайн (offline-режим нужен шлему, а не директору).

Исключение: `class.teacherId` хранится в документе класса (он синхронизируется), потому что учителю и шлему нужно знать класс офлайн. Меняется он только через серверное действие «передать класс» (ROLES 4.3, с записью в журнал); при синхронизации сервер всегда берёт `teacherId` из своей записи (сервер — источник правды поля).

**1.2. Таблицы (SQLite, миграция v3→v4).**

| Таблица | Поля | Индексы / ограничения |
|---|---|---|
| `schools` | `id TEXT PK, name, region TEXT DEFAULT '', status ('pending'/'active'/'archived'), network TEXT DEFAULT '', created, updated` | `schools_region(region, status)`; строка `school-default` создаётся миграцией |
| `users` | `id TEXT PK, login TEXT UNIQUE COLLATE NOCASE, name, email TEXT NULL` (почта отложена, Б16), `pw TEXT` (строка хэша, см. 1.3), `status ('active'/'archived'), pw_changed, created, updated` | `UNIQUE(login)` |
| `user_roles` | `user_id, role ('superadmin'/'director'/'teacher'/'expert'), school TEXT ('' для суперадмина), status, created, created_by` | `PK(user_id, role, school)`; `user_roles_school(school, role, status)` |
| `sessions` | `token_hash TEXT PK (sha256 токена), user_id, created, last_seen, expires, ip` | `sessions_user(user_id)` |
| `invites` | `code_hash TEXT PK, kind ('join'/'reset'), role, school, user_id (для reset), created_by, created, expires, used_at, used_by` | `invites_school(school)` |
| `login_fail` | `k TEXT PK` (логин или ip), `n, until, last` | — |
| `audit_log` | `id INTEGER PK AUTOINCREMENT, ts, actor_kind ('user'/'legacy-teacher'/'device'/'cli'), actor_id, action, target_kind, target_id, school, detail TEXT (JSON без секретов), ip` | `audit_school_ts(school, ts)`, `audit_target(target_kind, target_id)`; только INSERT, API удаления нет (А15) |
| `classes` (+колонка) | `teacherId TEXT` (производный индекс, правда — `doc`) | `classes_teacher(teacherId)`, `classes_school(school, status)` |

Список классов учителя не хранится у учителя, а выводится запросом `classes WHERE teacherId = ?` (одно место хранения, А11). Список школ учителя — строки `user_roles` с ролью `teacher`. Ученики остаются в таблице `students` (не в `users`): у них нет логина и пароля, только цифровой код входа (ROLES 7, Б34).

**1.3. Пароли.** `hashlib.pbkdf2_hmac('sha256', pw, salt, 600000)`, соль 16 байт из `secrets.token_bytes`, строка вида `pbkdf2_sha256$600000$<соль b64>$<хэш b64>` — параметры в строке, значит число итераций можно поднять позже без миграции (перехэш при следующем входе). Сравнение `hmac.compare_digest`. Хэширование вне глобального `lock` (иначе 0,5 с на Pi блокируют синхронизацию шлемов). Для неизвестного логина считается фиктивный хэш (одинаковое время ответа). Пароль: 10–128 символов, любые буквы/цифры/знаки, не равен логину, не из встроенного короткого списка частых паролей. Пароля по умолчанию нет: пароль задаёт сам человек при активации приглашения или кода сброса; суперадмин создаётся командой на сервере (1.6). Поле пароля — `type=password inputmode=text` (CHECKLIST, 22.10.2026).

Почему не scrypt: `hashlib.scrypt` зависит от сборки OpenSSL, PBKDF2 есть всегда и совпадает с тем, что уже есть в браузере (Web Crypto) — меньше сюрпризов на Pi.

**1.4. Сессии вместо общего ключа.** Вход `POST /api/auth/login {login, password}` → `{token, user, roles, expires}`. Токен `secrets.token_urlsafe(32)`, в базе только sha256 от него. Заголовок `Authorization: Bearer <token>` (заголовок, не cookie — нет CSRF; CORS добавить `Authorization` в `Allow-Headers`). Срок: простой настраивает суперадмин от 5 минут до 5 часов (по умолчанию 15 минут, как сейчас у страницы учителя), потолок сессии 12 часов не настраивается (решение владельца, раздел 5.5). Роли НЕ кладутся в токен: на каждом запросе сервер читает `user_roles` заново, поэтому снятие роли и архив действуют сразу. Смена пароля и сброс отзывают все сессии пользователя. Клиент хранит токен только в `sessionStorage` (закрыл вкладку — вышел; «К ученикам» = выход, Б34).

**1.5. Старые ключи (А6, А7).**
- Серверный флаг `accounts` в `/data/config.json` (рядом с `keys.json`, chmod 600; по умолчанию выключен). Это НЕ `settings.flags`: те синхронизируются и меняются ключом teacher, а флаг безопасности не должен включаться старым ключом. Пока флаг выключен, новые эндпоинты отвечают 404, поведение сервера прежнее.
- Ключ `teacher` = принципал `legacy-teacher`: права директора в `school-default` по данным (как сейчас: всё видит, всё меняет), но НЕ может вызывать администрирование учёток. Его действия пишутся в журнал с `actor_kind='legacy-teacher'`. Отключается только по слову владельца (`config.json: legacyTeacher=false`), после того как все учителя получили учётки.
- Ключ `device` = принципал `device` школы `school-default`: права не меняются (только добавлять учеников и результаты, Б34). Позже — ключи шлема по школам (шаг 12).
- Локальный пароль страницы учителя (`settings.pinHash`) остаётся рабочим, пока флаг выключен; при включённом флаге страница учителя входит по логину/паролю через сервер.

**1.6. Первый суперадмин.** Команда на сервере: `docker exec -it vr-lesson-api python3 /app/server/app.py create-superadmin <логин>` — пароль вводится дважды через `getpass` (не в аргументах, не в истории оболочки, не в чат, А14). Сброс пароля суперадмина — та же команда `reset-password`. Сетевого «первого входа» нет — нечего перехватить.

**1.7. Права по поддереву (А10, А17).** Одна функция `scope(c, principal)` → `{schools:set, classes:set|ALL, all:bool}` и одна `can(c, principal, action, target)`; все эндпоинты и `merge_in` идут через них.
- суперадмин: всё; агрегаты прогресса (ROLES п.3), полные данные учеников — только через действия администрирования.
- директор: всё в школах, где у него роль `director`; учётки учителей своей школы; ученики школы.
- учитель: классы с `teacherId = self` в школах, где он учитель; ученики этих классов; классы без учителя (`teacherId` пусто) видит только директор и `legacy-teacher`.
- ранг ролей: superadmin 4 > director 3 > teacher 2 > student 1; выдать можно только роль строго ниже своей и только в своём поддереве; директора назначает только суперадмин (ROLES п.3); свои роли менять нельзя (ROLES 4.8).
- запись вне поддерева в `merge_in` отбрасывается молча по записи, ответ содержит счётчик `rejected`, факт пишется в журнал (А13).

**1.8. Синхронизация по принципалу.** `merge_in(c, inc, role)` → `merge_in(c, inc, principal)`; `role == 'teacher'` превращается в `principal.can_edit(kind, doc)`. `state(c)` → `state(c, principal)`: возвращает только данные из `scope` (у принципалов `legacy-teacher` и `device` scope = `school-default`, то есть ровно как сейчас, пока школа одна). Правило слияния (lww, carry, объединение) не меняется — меняется только фильтр «что можно».

**1.9. Офлайн шлема.** Шлем остаётся на ключе `device` в `localStorage` (ему нужна автосинхронизация без человека). Вход ученика по коду — локально, как сейчас. Учётки взрослых шлему не нужны и в его данные не попадают.

**1.10. Клиентские модули (А1, А2).** Новый `js/auth.js` (ядро: вход, выход, токен, `auth.fetch`, `auth.user()`, `auth.can()` — только для показа кнопок) и новая страница кабинета `admin.html` + `js/admin.js` (директор и суперадмин). `teacher.html` получает только форму логина через `VR.auth`. Новые файлы — в `sw.js` FILES, версия кэша вверх (CHECKLIST).

### 2. Данные

- `school.region`: двузначный код субъекта РФ (`^[0-9]{2}$`) или пусто; сервер проверяет только формат, названия регионов — в клиентском справочнике `js/regions.js` (89 субъектов). Так сервер не зависит от файла сайта (А2).
- `class.teacherId`: строка 1–40 символов или отсутствует; в `js/schema.js` — новый проверяльщик `okTeacher` и отдельный список `CLASS_FIELDS=['teacherId']`, чтобы не задеть учеников. `carry`: у победителя без `teacherId` (старый клиент) берётся у проигравшего — то же в `server/app.py`, но сервер поверх этого всегда подставляет `teacherId` из своей записи (1.1).
- Учитель: школы — `user_roles`, классы — индекс `classes_teacher`.
- Индексы: `students_school(school,status)` (уже есть), `classes_school(school,status)`, `classes_teacher(teacherId)`, `schools_region(region,status)`, `user_roles_school(school,role,status)`.
- Версия схемы: сервер `SCHEMA=4`, клиент `VERSION=4`. Клиент v4 читает v2/v3 (А6); старый клиент v3 читает данные v4 (лишнее поле `teacherId` он отбрасывает, сервер вернёт его через carry).

**Миграция v3→v4 (`migrate_v4(c)`) по правилам CHECKLIST:**
1. В `init_db`: если `user_version < 4` и база существовала — `backup_db('v3')` до любых изменений; не удалась копия — остановка (`sys.exit(1)`), как сейчас.
2. Сначала `migrate_v3` (как есть), затем `migrate_v4` — в своей явной транзакции `BEGIN IMMEDIATE … COMMIT`, при ошибке `ROLLBACK` (Python 3.13 не открывает транзакцию перед DDL).
3. Внутри: `CREATE TABLE IF NOT EXISTS` всех новых таблиц; `ALTER TABLE classes ADD COLUMN teacherId TEXT`, если её нет; заполнить `teacherId` из `doc` (у текущих классов его нет — останется NULL); `INSERT OR IGNORE INTO schools` строку `school-default`; индексы; `PRAGMA user_version = 4`.
4. Идемпотентна, запускается на каждом старте; ничего не удаляет (А15).

**Слияние — оба места одновременно (А11):** `js/schema.js` (`carry`, `fill` для `classes`), `js/store.js` (`merge` вызывает их, сама логика lww не меняется) и `server/app.py` (`fill_v3` → `fill_v4(doc, old, kind, device_new)` + правило «teacherId от сервера»). Проверка равенства: один и тот же набор пар (старый клиент / новый клиент) прогоняется через `merge` в Node и через `merge_in` на живом сервере, результаты по классам сравниваются.

### 3. Шаги реализации

Пуш — по скиллу `vr-lesson-push`, релизная ветка перед шагами 1, 6 и 13.

**Шаг 1. Миграция сервера v3→v4 (только DDL, без поведения).**
- Что меняем: `server/app.py` (`SCHEMA=4`, `migrate_v4`, вызов в `init_db`, копия `bak-v3`), новый `tests/fixtures/make_v3_db.py` (делает v3-базу из `legacy-v2.json` текущим кодом), `tests/run.js`.
- Тесты (`run.js`): v3-база с учениками и результатами → старт → `user_version=4`, есть `*.bak-v3-*`, `state()` побайтно равен до/после (кроме `v`), есть строка `school-default`, второй старт ничего не меняет; обрыв миграции на середине (подмена функции, как в тесте v2→v3) → база осталась v3 и целой, повторный старт даёт v4. `/api/health` → `schema: 4`.
- Модель: Sonnet, ревью Opus (данные).
- Законы: А5, А6, А8, А15.
- Риск: сломать старт сервера на VPS. Откат: релизная ветка + копия `bak-v3`; старый код v3 открывает базу v4 (новые таблицы и колонка ему не мешают) — проверить это в тесте (старт кода из ветки `release-v3.1` на базе v4 не падает).

**Шаг 2. `teacherId` в схеме и слиянии (оба места).**
- Что меняем: `js/schema.js` (VERSION 4, `okTeacher`, `CLASS_FIELDS`, `carry`/`fill` для классов), `js/store.js` (merge передаёт kind в carry), `server/app.py` (`fill_v4`, запись колонки `teacherId`, правило «teacherId из записи сервера»), `sw.js`, `tests/run.js`.
- Тесты: старый клиент (класс без `teacherId`) перезаписывает класс с `teacherId` → поле сохраняется и в `merge`, и на сервере; одинаковый результат `merge` (Node) и сервера на одном наборе; ключ шлема и `legacy-teacher` не могут поставить или сменить `teacherId` через sync; данные `legacy-v2.json` читаются клиентом v4; `tests/laws.js` зелёный (порядок вопросов не тронут).
- Модель: Sonnet, ревью Opus (слияние).
- Законы: А5, А6, А11.
- Риск: расхождение `merge`/`merge_in` → «воскрешение» или потеря поля. Откат: revert коммита; данные не теряются (поле только добавляется).

**Шаг 3. Журнал аудита для текущих действий.**
- Что меняем: `server/app.py` (`audit(c, principal, action, target_kind, target_id, school, detail)` в той же транзакции; вызовы в `merge_in` для: смены кода ученика (`pinHash` изменился — пишем факт, не значение), архив/возврат, `deleted`, смена `settings` (имена ключей, без значений `pinHash/pinSalt`), создание класса, ученик от шлема), `tests/run.js`.

- Модель: Sonnet, ревью Opus (что считается секретом).
- Законы: А13, А14, А17, ROLES 4.5.
- Риск: рост базы. Мера: пишем только изменения; ротации/удаления нет (А15) — вопрос объёма вернётся при росте. Откат: revert, таблица остаётся.

### 5. Решения владельца (22.10.2026)

1. **«Четыре глаза» при смене директора, пока суперадмин один.** Принято по умолчанию: повторный ввод пароля и 24 ч на отмену, всё в журнале. Со вторым суперадмином — подтверждение вторым человеком.
2. **Старый ключ teacher отключается, когда он не нужен.** «Не нужен» проверяется по фактам, не по дате: у каждого учителя и директора школы по умолчанию есть учётка, и 14 дней в журнале нет действий `legacy-teacher`. Кабинет суперадмина показывает готовность («можно отключать: да/нет», у кого ещё нет учётки, когда ключ использовали в последний раз). Выключатель нажимает суперадмин, сам ключ не гаснет (иначе школа может потерять вход посреди урока). Откат — `legacyTeacher=true` в `config.json`. Автоотключение после N спокойных дней добавим по слову владельца.
3. **Ключи шлемов — обязательны до подключения второй школы, и это контроль устройств для тарифов.** Меняется шаг 12: ключ на каждый шлем, а не на школу (см. шаг 12, лимит устройств по тарифу, привязка по короткому коду).
4. **Логин: баланс удобства и безопасности (вариант в плане, меняется до шага 4).**
   - Логин: латиница, цифры, `.` `_` `-`, 3–32 символа, без учёта регистра, уникальный на всей платформе (экран входа один, школу выбирать не нужно). Кириллицу не допускаем: нет визуальных двойников («а» русская и латинская).
   - Предлагает сервер: фамилия.инициалы латиницей, человек может поправить один раз при активации приглашения. Конфликт — суффикс.
   - Почта не обязательна (Б16 отложено): поле `email` в `users` создаём пустым, вход по почте подключим позже поверх.
   - Суперадмин задаёт свой логин сам; зарезервированы `admin`, `root`, `superadmin`, `director`, `teacher`.
   - Безопасность: на экране входа нет списка учителей (в отличие от входа ученика), одинаковый ответ и время для «нет логина» и «неверный пароль», лимиты по логину и IP (раздел 4).
   - Пароль: 10–128 символов, длинная фраза приветствуется, обязательной смеси символов нет, проверка по списку частых паролей.
   - Вход ученика не меняется: класс → имя → цифровой код.
5. **Срок сессии настраивает суперадмин: простой от 5 минут до 5 часов (по умолчанию 15 минут).** Сервер отклоняет значения вне диапазона, смена пишется в журнал, действует на открытые сессии со следующего запроса. Потолок сессии 12 часов остаётся фиксированным и не настраивается (решим, если станет принципиально). Задаётся командой `set-session-minutes` (шаг 5) и полем в кабинете суперадмина (шаг 10).

### Б74.2. Решения по архитектуре

**Надгробия: мягкие и жёсткие.**
- Таблица `deleted` (как сейчас) — надгробия, которые получают клиенты. Новая таблица `purged(id TEXT PRIMARY KEY, ts INTEGER NOT NULL, kind TEXT)` — жёсткие надгробия: запись стёрта окончательно. Пишет её только окончательное стирание (и миграция, см. Б74.3). При стирании id пишется **в обе** таблицы — тогда откат на старый код (он знает только `deleted`) не даст старому клиенту «воскресить» стёртое (А8).
- `state()` отдаёт `deleted` = объединение `deleted` и `purged` (старые клиенты удаляют у себя всё это, как сейчас) и новое поле `purged` = карта `purged` (новые клиенты отличают жёсткое от мягкого).
- Клиент `purged` на сервер не передаёт, а сервер присланное `purged` **игнорирует**: окончательно стереть через синхронизацию нельзя никому.

**Правило слияния (одинаковое в `js/store.js` merge и `server/app.py` merge_in, А11):**
1. `hard` = объединение `purged` обеих сторон (на сервере — таблица `purged`). Запись любого вида с `id` в `hard` отбрасывается; результаты и открытия ученика `sid` из `hard` отбрасываются.
2. Ученики и классы: сначала обычный lww (как сейчас, с `carry`/`fill`). Затем, если у победителя `x` есть мягкое надгробие `del[x.id]` (и id не в `hard`), `del[x.id] > (x.updated||0)` и `x.status !== 'archived'`, то `x` = копия с `status:'archived'`, `updated: del[x.id]`. Иначе надгробие для учеников и классов ничего не делает. Возврат из архива ставит `updated = max(now, old.updated+1)` (как `_setStatus`), поэтому повторно присланное старым клиентом надгробие возврат не отменяет.
3. Результаты и открытия: убрать фильтр `del[r.sid]` (ученик в архиве — результаты живут); оставить фильтры `hard[r.sid]`, `del[r.id]`, `hard[r.id]`, `ts >= resetAt`. Открытия: фильтр `hard[sid]` вместо `del[sid]`.
4. Тесты и отзывы: как сейчас (`del[id]` или `hard[id]` → отброшены).
5. Сервер: надгробие ученика или класса **не пишется** в таблицу `deleted` (иначе старые клиенты v3 потеряют запись из своей вкладки «Архив»); пишется только аудит `student.archive`/`class.archive` c `detail {'via': 'tombstone'}`. Надгробие на неизвестный id: для `legacy-teacher` — как сейчас (пишется в `deleted`), для пользователя — отказ (как сейчас, `tests/scope.py`).
6. Порядок на сервере: в цикле `deleted` надгробие применяется к записи в базе (lww против её `updated`), затем идёт обычный цикл учеников/классов. Это даёт тот же итог, что и клиентский порядок (lww, затем надгробие): побеждает самая поздняя из трёх правок (база, присланная запись, надгробие). Проверяется тестом равенства.
- Ключ шлема (`role != 'teacher'`): надгробия по-прежнему не принимаются вовсе; удалять и архивировать шлем не может (Б34).
- Старые клиенты: старый учитель удаляет ученика → сервер архивирует; старый клиент у себя запись не видит и шлёт надгробие при каждой синхронизации — это пустое действие (`ts` не больше `updated`). Клиенты v2 (без поля `status`) покажут архивного ученика активным — риск принят, их не должно остаться (sw.js обновляет кэш); проверить в CHECKLIST.

**Корзина `trash`** (для видов без поля `status`): `trash(kind TEXT NOT NULL, id TEXT NOT NULL, school TEXT, doc TEXT NOT NULL, ts INTEGER NOT NULL, actor_kind TEXT, actor_id TEXT, PRIMARY KEY(kind, id))`, индекс `trash_school(school, ts)`. Виды: `test`, `feedback`, `result`, `room`, `open_room`. `school` — `school-default` для тестов, отзывов и комнат (настройки пока общие), школа ученика для результата, школа строки для `open_room`. Возврат (`trash.restore`) создаёт **копию с новым id** (у клиентов надгробие старого id остаётся навсегда), запись в корзине помечается `doc` без изменений, строка корзины удаляется только окончательным стиранием.

**Окончательное стирание (purge).**
- Кто: только суперадмин (`rank >= SUPER`). Чем: `POST /api/admin/purge` с повторным вводом пароля по тому же пути, что смена директора (`need_pw` в `admin_api`, `throttle`/`register_fail` с ключом `'adm:' + login`). Предпросмотр `POST /api/admin/purge.preview` — без пароля, только суперадмин.
- Флаг: `config.json` → `purge` (по умолчанию `false`), команда `python3 server/app.py purge on|off` (как `open-rooms`); при выключенном флаге оба действия отвечают 404 (А7).
- Что можно стереть: только то, что уже в архиве/корзине. Виды и правила:
  - `student`: `status='archived'`. Стираются строки `students`, `results` (вместе с закрытыми), `disc`; в отзывах с `sid` = id поле `sid` убирается (отзыв остаётся анонимным). id → `purged` и `deleted`.
  - `class`: `status='archived'`, и все ученики с этим `classId` в архиве (иначе 400 «В классе есть действующие ученики: N»); стирается класс и каскадом его ученики (по правилу `student`).
  - `user`: `users.status='archived'`, не сам себя. Строка не удаляется, а обезличивается: `login='x-'+token_hex(6)`, `name=''`, `email=NULL`, `pw=''`, `updated=now`; удаляются его `sessions` и `invites` (`user_id`); строки `user_roles` остаются (история ролей). Проверить, что `check_pw(любой, '')` возвращает `False`.
  - `school`: `status='archived'`, не `school-default`, и пусто: нет классов, учеников, активных `user_roles`, активных шлемов, `uploads`, `open_rooms` (иначе 400 со счётчиками). Удаляются строка `schools`, отозванные `devices` и `pair_codes` школы. Регион и район исчезают из фильтров сами (Б74 текст закона).
  - `upload`: `archived_at IS NOT NULL`; удаляется строка и файл (`os.remove`; ошибка удаления файла — в `detail {'file': 'missing'}`, не молча, А13).
  - `trash`: строки корзины по `(kind, id)`.
  - `reset`: результаты и открытия с `ts < resetAt` (без id).
- Пакет: `ids` — список до 50 id одного вида (лимит тела для `/purge` — 8192 байт, для остальных как сейчас 4096).
- Копия перед стиранием: в `admin_api` для `purge` — после проверки пароля, **под `lock`, до открытия транзакции**: проверка места (`shutil.disk_usage(DATA).free > 2 * размер базы`, иначе 507 «Мало места для копии, стирание отменено»), затем `backup_db('purge')` (файл `vrlesson.db.bak-purge-<время>`, chmod 600). Копия не удалась → стирания нет, ответ 500 с понятным текстом, аудит `purge.failed` отдельной короткой транзакцией. Затем в той же блокировке транзакция стирания (`admin_action`). Файлы `uploads` копируются только ночным `deploy/backup.sh` (хранит 14) — это сказать в окне подтверждения.
- Необратимость: всё в одной транзакции; ответ `{ok, purged: n, backup: '<имя файла без пути>'}`. Сказать честно (в окне и справке): данные остаются в копиях до их ротации — `bak-purge-*` (ротации нет, см. вопросы) и ночные копии (14 дней, VPS и Pi).
- Аудит (без секретов, без ФИО): по одной строке `purge` на каждый стёртый объект: `target_kind`, `target_id`, `school`, `detail {'results': n, 'disc': n, 'feedback_anonymized': n, 'students': n (для класса), 'backup': '<имя файла>'}`; для класса допустимо `name` вида «5А», для школы — её название; имя ученика и пользователя — нет. Прежние строки журнала не трогаются (А15).

**История по школе: `GET /api/history`.**
- Параметры: `school` (обязателен; суперадмин может передать `-` — строки без школы), `kind` (`all`|`user`|`student`|`class`|`school`|`device`|`upload`|`room`), `from`, `to` (мс), `page`, `size` (≤ `PAGE_MAX`=100, по умолчанию 50). Ответ `{items, page, size, more}` (берём `size+1` строк, без `count(*)` по журналу).
- Права (через `scope` и `scope_schools`): суперадмин — любая школа; администратор региона/района и директор — школы из `scope_schools(c, scope(c, p))`; учитель, специалист, ученик, ключи — 403 (развилка — вопрос 3). Флаг `accounts` выключен → 404 (как `/api/accounts`).
- Выборка: `school = ?` ИЛИ (`target_kind='user'` И `target_id` в списке пользователей, у которых есть строка `user_roles` в этой школе в любом статусе) — так находятся `user.archive/restore`, где `school` пустой. Сортировка `ts DESC, id DESC`. Индексы `audit_school_ts` и `audit_target`; в тесте `EXPLAIN QUERY PLAN` без `SCAN audit_log`.
- Строка ответа: `{ts, action, kind, target, name, actor, detail}`. `name` — текущее имя цели (ученик/класс/пользователь/школа одним пакетным запросом на страницу; стёрто или не найдено → `''`, интерфейс пишет «стёрто»). `actor` — имя пользователя или `ключ учителя` / `шлем` / `сервер`. `detail` — только ключи из белого списка: `role, name, from, to, status, students, results, count, keys, by, via, why, action, classId, had, title, auto, device_limit, truncated, disc, feedback_anonymized`. Поле `ip` не отдаётся никому (вопрос 6). Хэшей, кодов, токенов в журнале нет по закону, белый список — вторая защита.

### Б74.5. Риски и что проверить ревью (Opus)

1. **Равенство слияния** (шаг 19): тест равенства действительно гоняет один набор через Node и живой сервер; порядок «надгробие → lww» на сервере и «lww → надгробие» в клиенте дают одно и то же на всех краевых случаях (включая равные `updated`).
2. **Воскрешение**: id из `purged` отбрасывается во всех ветках `merge_in` (ученики, классы, результаты, открытия, отзывы, тесты) и в клиентском `merge`; миграция переносит все старые `deleted` в `purged`; при откате на старый код стёртое остаётся в `deleted`.
3. **Стирание старыми клиентами**: после шага 19 ни один путь синхронизации не делает `DELETE` по ученикам, классам, результатам (кроме `purged`); grep `DELETE FROM` в `merge_in` — только по `purged`.
4. **Ключ шлема** ничего не архивирует, не стирает и не возвращает; присланные `purged` и надгробия от шлема игнорируются.
5. **Стирание**: только суперадмин, только архивное, пароль проверяется до копии и транзакции, копия до транзакции и под `lock`, всё стирание — одна транзакция; путь копии в ответе — только имя файла; `need_pw` нельзя обойти другим именем действия.
6. **История**: срез по `scope_schools`, белый список `detail`, нет `ip`, нет хэшей; учитель и специалист не получают историю; объединение с `target_kind='user'` не тянет пользователей чужих школ.
7. **Рост базы и диска**: скрытые результаты, корзина, архивные файлы, копии `bak-purge-*` растут без ротации (А15) — нужна договорённость с владельцем (вопрос 2).
8. **Блокировка**: копия базы под `lock` останавливает синхронизацию шлемов на время копии (секунды на большой базе) — приемлемо для редкого действия, но проверить на `tests/` с 18 000 учеников и описать в HANDOFF.
9. **152-ФЗ**: окончательно стёртое остаётся в копиях до их ротации; это должно быть сказано владельцу и в окне подтверждения.
10. **ROLES 4.2 и 4.6** требуют «двух людей» для стирания данных ученика и удаления школы; по решению владельца сейчас это повторный пароль суперадмина (как PLAN 5.1). При появлении второго суперадмина — подтверждение вторым человеком; текст ROLES правит Айрат.
