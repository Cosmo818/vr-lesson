# Формат комнаты (RoomSpec) v1 — проект

Статус: черновик на утверждение. Кода пока нет. Цель — комнаты, которые делают учителя, а не программисты, и которые безопасно запускать на устройствах детей.

## 1. Принципы

1. **Комната — это данные (JSON), а не код.** Чужой код на шлемах детей запускать нельзя. Общий движок читает описание и рисует его.
2. **Только разрешённые блоки и действия.** Что не в списке — не выполняется.
3. **Неизменяемые версии.** Опубликованная версия не меняется; правка = новая версия. Класс привязан к версии, урок не ломается от чужой правки.
4. **Комната не видит данные учеников.** Она отправляет только события («вопрос решён», «предмет найден»), а имена, классы и коды остаются у платформы.
5. **Не зависит от движка.** Формат описывает «что», а не «чем рисовать». Выбор Babylon.js или своего движка (после замера на Quest 1) не меняет формат.
6. **Бюджет производительности заложен в формат** (раздел 5): редактор сам считает «стоимость» комнаты и говорит, на каких шлемах она пойдёт.

## 2. Что есть сейчас и что меняется

| Сейчас | Нужно для платформы |
|---|---|
| Два общих ключа: `teacher` и `device` на весь сервер | Аккаунты учителей, привязка к школе, роли (учитель, эксперт, админ); ключ шлема на школу |
| Комнаты — код в `rooms*.js` | Комнаты — JSON; старые остаются как «встроенные», новые идут через общий рендерер |
| Тесты учителя (`tests`) | Остаются отдельной сущностью; блок `quiz` ссылается на тест по id |
| Один сервер | Центр (vrklass.ru) + школьный узел с кэшем комнат и медиа (раздел 9) |

Текущая логика слияния (`js/store.js` `merge` и `server/app.py` `merge_in`, побеждает свежая правка по `updated`) годится для тестов и классов. Комнаты добавляются как новая сущность с иными правилами: версии неизменяемы, поэтому конфликтов правок нет, есть только новые версии.

## 3. Формат комнаты (пример)

```json
{
  "schema": "room/1",
  "id": "r_8f3k2",
  "version": 3,
  "title": "Клетка изнутри",
  "subject": "bio",
  "grades": [5, 7],
  "lang": "ru",
  "author": "u_teacher_17",
  "license": "free",
  "profile": "standard",
  "env": { "preset": "lab", "light": "day" },
  "spawn": { "x": 0, "z": 4, "yaw": 3.14 },
  "assets": [
    { "id": "a_cell", "kind": "model", "ref": "lib:cell-animal-v2" },
    { "id": "a_ding", "kind": "sound", "ref": "lib:ding" }
  ],
  "blocks": [
    { "id": "b1", "type": "text", "pos": [0, 1.8, -3], "w": 2.4, "text": "Найди ядро клетки" },
    { "id": "b2", "type": "model", "asset": "a_cell", "pos": [0, 1.2, -2], "scale": 1.0, "grab": true },
    { "id": "b3", "type": "hotspot", "target": "b2.part.nucleus", "label": "Ядро",
      "on": [{ "do": "sound", "asset": "a_ding" }, { "do": "discover", "key": "nucleus" }, { "do": "score", "points": 1 }] },
    { "id": "b4", "type": "quiz", "test": "t_cell_5", "pos": [3, 1.5, 0] },
    { "id": "b5", "type": "portal", "to": "hall", "pos": [-4, 1, 0] }
  ],
  "goal": { "type": "all", "of": ["nucleus", "quiz:t_cell_5"] }
}
```

Служебные поля при публикации ставит платформа, автор их не меняет: `hash` версии, `cost` (стоимость), `status`, `createdAt`.

## 4. Блоки и действия v1

**Блоки**

| Тип | Что делает |
|---|---|
| `text` | Панель с текстом (ограничение длины, без HTML) |
| `image` | Картинка из библиотеки или загруженная после модерации |
| `model` | Модель из библиотеки (glTF), можно брать в руки (`grab`) |
| `hotspot` | Точка на модели или в пространстве; срабатывает на указание/касание |
| `quiz` | Тест учителя по id (используем существующий конструктор тестов) |
| `portal` | Переход в другую комнату (встроенную или по id) |
| `item` | Простой предмет с физикой (куб, шар, цилиндр) из каталога |
| `sound` | Звук: фоновый или по событию |
| `video` | Позже (v1.1): ролик из библиотеки, нужен медиа-узел |

**Действия** (`on`): `sound`, `text`, `discover`, `score`, `unlock`, `show` / `hide`, `teleport`. Условия: `once`, `after:<id>`. Циклов, формул и своего кода нет.

**Цель комнаты** (`goal`): список ключей (`discover`, результат теста) и условие `all` / `any`. Когда цель выполнена, платформа засчитывает комнату ученику.

## 5. Бюджет производительности

Замер на Quest 3 (через страницу `bench/`): лёгкая сцена даёт ~89 к/с в VR, тяжёлая (400 отдельных объектов с PBR, текстуры 2048, тени) уже ~67 к/с. Замер на Quest 1 ещё впереди. Поэтому формат содержит профили:

| Профиль | Для кого | Лимиты (первоначальные, уточнить по замеру Quest 1) |
|---|---|---|
| `lite` | Quest 1 | объектов ≤ 60, текстуры ≤ 512 px, без теней, простые материалы, треугольников ≤ 100 тыс. |
| `standard` | Quest 2/3 | объектов ≤ 200, текстуры ≤ 1024 px, тени ≤ 1 источника, треугольников ≤ 400 тыс. |

Редактор считает `cost` и показывает «пойдёт на Quest 1 / только на Quest 2 и новее». Платформа не публикует комнату выше лимита выбранного профиля. Учитель видит это до публикации, а не после жалоб учеников.

## 6. Безопасность и модерация

- **Никакого исполняемого кода** в комнате. Схема валидируется на сервере по белому списку; неизвестные поля отбрасываются.
- **Текст** — только простой, без разметки; ограничения длины; фильтр недопустимого.
- **Загрузка своих файлов** (картинки, модели, звук) — только через очередь модерации; сначала доступна только библиотека платформы.
- **Статусы:** `draft` (черновик автора) → `review` (проверка) → `published` → `retired` (скрыта, но у классов, которые её уже используют, работает).
- **Модерация:** учителя-эксперты проверяют содержание и фактическую точность; для предметов с политической чувствительностью (история, обществознание) — отдельная проверка.
- **Права:** автор правит только свои комнаты; чужую можно только форкнуть (копия с пометкой автора оригинала).
- **Жалобы** на комнату доступны учителю одной кнопкой; при серии жалоб комната временно скрывается до проверки.
- **Дети:** комната не получает имён, классов, кодов. Все персональные данные остаются в платформе (152-ФЗ отдельным этапом).

## 7. Версии, публикация, форки

- Идентификатор `id` постоянный, версия — число. Опубликованная версия неизменяема; у неё хэш.
- Учитель назначает классу версию. Новая версия подтягивается только по его решению.
- Форк: копия с новым `id`, поле `forkOf` указывает на оригинал. Автор оригинала получает долю в рейтинге и отчислениях по заранее заданным правилам (см. раздел 8).
- Откат: возврат к предыдущей версии комнаты одной кнопкой.

## 8. Рейтинг и монетизация

**Сигналы рейтинга** (все считаются без персональных данных):

1. Оценки учителей, которые реально проводили урок (не любые пользователи).
2. Доля учеников, завершивших комнату (`goal`).
3. Результаты связанного теста до и после.
4. Повторное использование: сколько классов вернулись к комнате.
5. Жалобы (снижают вес).
6. Метка «проверено экспертом».

Итог: байесовское среднее по сигналам (как уже сделано для классов), чтобы одна оценка не поднимала комнату на первое место. Защита от накруток: один голос на школу, голос только после проведённого урока, учителя-авторы не оценивают свои комнаты.

**Монетизация — в формат закладываем поля, включаем позже:**

- `license`: `free` | `paid` | `school` (по подписке школы). Плюс `price` для платных.
- Учёт использования: события «комната × версия × школа × число уникальных учеников за месяц». Имён и идентификаторов учеников в событии нет.
- Отчисления автору: пропорционально реальному использованию (активные ученики), а не числу «подписчиков». Доля платформы фиксированная; конкретные проценты определяются позже по выручке.
- Выплаты физлицам требуют договора и налогового учёта, это отдельный этап с юристом. Сейчас достаточно хранить события.

## 9. Архитектура: центр и школьный узел

- **Центр** (vrklass.ru): аккаунты, каталог комнат, рейтинг, модерация, учёт использования.
- **Школьный узел** (мини-ПК в сети школы): локальный кэш комнат и медиа, раздаёт файлы быстро по локальной сети, работает без интернета, затем синхронизируется с центром. Адрес сервера в приложении становится списком: сначала локальный, потом облако.
- **Общие комнаты** (несколько учеников вместе): WebSocket для событий и WebRTC для голоса; сервер сессии на школьном узле или в центре. Отдельный этап, формат комнаты уже содержит поля `spawn` и идентификаторы блоков, которые понадобятся для синхронизации.
- **Ключи:** общий ключ `teacher` и общий ключ шлема заменяются аккаунтами учителей и ключом шлема на школу. Миграция делается поэтапно, чтобы текущая школа не потеряла доступ.

## 10. Совместимость с текущим кодом

- Рендерер RoomSpec — это адаптер: из JSON он собирает объект `VR.ROOMS.<id>` по существующему контракту комнаты (`build`, `targets`, `update`, `draw`, `onGrab`, `onRelease`). Старые комнаты остаются как есть.
- Сущность `test` не меняется. Блок `quiz` вызывает существующий `VR.makeQuiz`.
- Состояние `Store` получает новые разделы: `rooms` (локальный кэш), `roomUsage` (события). Для них нужна своя логика слияния в `store.js` и `server/app.py` (менять оба места).

## 11. Редактор

1. **2D-редактор** в `teacher.html`: список блоков, поля, предпросмотр сцены, счётчик стоимости, кнопка «Опубликовать».
2. **Правка в шлеме:** расставить блоки руками, сохранить в тот же JSON.
3. **Шаблоны:** «лабораторная», «экскурсия», «квест», чтобы учитель начинал не с пустого места.

## 12. План внедрения

| Этап | Результат | Критерий готовности | Модель |
|---|---|---|---|
| 0 | Замер на Quest 1, выбор библиотеки | Цифры по трём уровням, решение «Babylon.js / свой» | Opus (решение) |

## 13. Решения за владельцем

1. Первые профили: оставляем только `lite` и `standard` или нужен третий (`high` для Quest 3)?
2. Кто модерирует на старте: только владелец или сразу привлекаем учителей-экспертов?
3. Лицензии комнат: свободные (например, CC BY) и платные одновременно, или сначала только свободные?
4. Можно ли учителю использовать в комнате загруженные им картинки и звуки до модерации, если они видны только его классу?
5. Нужна ли привязка комнат к школьной программе (ФГОС/темы) уже в первой версии?
